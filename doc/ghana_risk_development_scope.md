# GalaCredit 加纳风控策略开发边界

## 一、可以直接开发完成的部分

### 1. 统一风控决策引擎基础设施

可以直接完成：

- `risk_decision` 决策记录。
- `risk_feature_snapshot` 特征快照。
- `risk_rule_hit` 规则命中明细。
- `risk_policy_version` 策略版本、启停、灰度和回滚。
- 标准决策结果：`APPROVE`、`APPROVE_LOW`、`REFER`、`DECLINE`、`BLOCK`。
- 标准 reason code 字典和中英文运营解释。
- 每次决策绑定用户、订单、渠道、策略版本、模型版本、操作者和时间。
- 业务失败不改变现有 API 响应规范，所有决策异常保留审计记录。

### 2. 基于现有字段的硬规则

可以直接使用当前系统已有的黑名单、风险名单、KYC、人脸、GPS/IP、位置风控、授信、逾期和渠道字段开发：

- 黑名单/风险名单命中阻断。
- 身份证号、手机号、姓名重复或冲突。
- 实名、人脸未完成的低额限制或人工审核。
- 位置风控锁定和人工解锁审计。
- 逾期未结清锁定可用额度。
- 同一用户未结清订单限制。
- 同一渠道的风险状态和渠道观察期。
- 放款前重新检查 KYC、黑名单、风险名单、额度和收款信息。

### 3. 规则化 Fraud Score 和 Credit Score

第一阶段不依赖机器学习，可以开发可解释的规则评分：

- Fraud Score：身份、设备/网络、钱包、行为速度、关联关系、地理合理性。
- Credit Score：历史还款、当前负债、现金流、资料完整性、渠道表现。
- 分数区间、命中原因、人工复核阈值可配置。
- 先以 shadow mode 运行，只记录建议结果，不改变实际审批。
- 通过真实还款周期验证后，再切换到 champion 策略。

### 4. 额度、期限和复贷阶梯

可以开发产品/策略配置：

- 新客、首贷、复贷、逾期客户的额度矩阵。
- 期限矩阵和最大可用额度。
- 还款能力比例约束，如 PTI/DTI 的规则计算框架。
- 逾期、欺诈、资料不完整时自动降额或禁止提额。
- 按渠道、产品、客群和策略版本配置。
- 额度变更前后快照、审批人和原因记录。

### 5. KYC 与人工审核运营闭环

可以直接完成：

- KYC 队列优先级：欺诈、身份冲突、资料缺失、服务异常。
- 通过/拒绝/批量处理/备注/复核人/复核时间。
- 人工覆盖原决策必须填写原因。
- SLA、超时、退回补件、二次复核。
- KYC 规则命中和处理结果回写风险决策记录。

### 6. 设备、IP 和速度规则框架

后端和数据库框架可以直接开发：

- 设备指纹、设备首次出现时间、关联用户数。
- IP、ASN、代理/VPN、时区和语言环境记录。
- 注册、OTP、KYC 上传、申请、放款的速度特征。
- 同设备/手机号/身份证/渠道的关联图基础数据。
- 规则阈值、观察窗口和命中原因。

注意：H5 浏览器能采集的设备信号有限；如果要取得更完整的 Root、模拟器、应用完整性和设备硬件信号，需要原生 App 或合规 SDK。

### 7. 风控和运营监控

可以直接开发：

- 审批漏斗和决策结果分布。
- Fraud hit rate、REFER 率、人工覆盖率。
- FPD1/7/30、Vintage、Roll-rate。
- 渠道 cohort、产品 cohort、客群 cohort。
- 策略版本对比、champion/challenger。
- 规则命中排行和误杀复核。
- 贷款/用户/任务下钻。
- 投诉、催收、平账、支付失败和数据质量监控。

### 8. 贷后、逾期和催收自动化框架

可以开发：

- D-3、D-1、D0、D1-D3、D4-D7、D8-D30、D30+ 阶段策略。
- 消息模板、发送结果、客户时区和模板版本回溯。
- 承诺还款、困难客户、跟进结果和催收分配。
- 自动锁定复贷额度和解除条件。
- 催收任务 SLA、升级、转派、抽检和审计。

催收话术、频率、第三方外包和法律动作仍需合规审批。

### 9. 数据治理和策略审计

可以直接开发：

- 数据授权记录、访问日志、导出日志和纠错记录。
- 敏感字段脱敏、最小权限和管理员登录历史。
- 策略发布审批、版本比较、回滚。
- 决策重放：使用历史特征快照重新计算，检查规则变化影响。
- 数据保留期限和删除任务框架。

## 二、需要外部服务、合同或凭据后才能完成的部分

### 1. Ghana Card/NIA 实时核验

我可以开发供应商适配器、超时、重试、缓存、降级和审计，但不能凭空获得 NIA 或授权身份服务权限。需要：

- 合法供应商或 NIA 授权。
- API 文档、测试账号、生产凭据和费用规则。
- 数据处理协议、用户授权文本和错误码说明。

### 2. Ghana Mobile Money 实名和现金流核验

我可以开发 MTN MoMo、Telecel Cash 等供应商的适配层、钱包一致性检查、支付回调、幂等和对账，但需要：

- 具体支付机构/聚合商。
- API、webhook、签名规则和沙箱账号。
- 允许查询的字段范围和用户授权方式。

### 3. 加纳征信查询与报送

我可以开发 credit bureau adapter、授权记录、查询缓存、纠错流程和报送文件，但需要：

- 持牌机构身份和征信机构合同。
- 查询/报送 API 或文件规范。
- 计费、授权、纠错和保留要求。

### 4. 反洗钱、制裁和 PEP 数据源

我可以开发名单导入、匹配、模糊比对、人工复核和审计，但需要合规的数据源、更新频率和处置规则。不能仅凭普通公开网页构成生产制裁筛查依据。

### 5. 完整移动设备风险 SDK

我可以完成服务端接收、评分和策略联动，但 Root、模拟器、应用篡改、硬件级指纹等能力需要原生 SDK、PWA 能力或第三方设备风险服务，并需通过隐私合规评审。

## 三、不能由我单独决定的部分

以下内容我可以提供测算、方案、配置和测试，但不能替你作最终业务/法律决定：

- 牌照范围、是否可提供数字信贷、合作方责任边界。
- 利息、费用、逾期费、总成本和展示方式。
- 最大额度、最长期限和 affordability 阈值的最终批准值。
- 是否报送征信、报送频率和纠错时限。
- GPS、联系人、钱包流水和设备数据的授权范围。
- 催收频率、时间窗口、话术和第三方外包。
- 制裁、PEP、AML 命中后的最终处置。
- 对特定地区、职业或客群的差异化策略是否公平、合法。
- 核销、减免、法律追偿和负面信息报送政策。

## 四、推荐开发顺序

### Phase 1：风控基础设施

1. 策略版本、决策日志、规则命中、reason code。
2. 现有黑名单、风险名单、KYC、位置、逾期规则统一接入。
3. 决策重放、审计、人工覆盖和后台配置。

### Phase 2：规则评分和运营闭环

1. Fraud Score/Credit Score 规则版。
2. 首贷/复贷额度矩阵和 PTI/DTI 框架。
3. KYC、人工审核、贷后和渠道监控。

### Phase 3：设备、速度和关联网络

1. 设备/IP/ASN/代理和速度特征。
2. 设备—手机号—身份证—渠道关联图。
3. 新客 shadow mode 和策略灰度。

### Phase 4：外部数据和模型化

1. Ghana Card/NIA、Mobile Money、征信和 AML 供应商接入。
2. 现金流和征信特征。
3. 经合规批准的统计模型/机器学习模型。

## 五、建议的第一批开发验收标准

- 每笔申请有唯一 `decision_id`、`policy_version` 和特征快照。
- 每个拒绝、降额或人工审核都有 1–3 个标准 reason code。
- 规则修改可启停、版本比较、灰度和回滚。
- 不接外部服务时仍可使用现有字段完成安全降级。
- KYC、风控、放款前复核、催收和人工覆盖全部可审计。
- 先 shadow mode，再小流量灰度，不直接改变全量放款结果。
- 所有外部数据只在授权和合规评审通过后进入生产决策。
