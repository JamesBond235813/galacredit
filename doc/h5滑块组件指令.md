# H5 滑块验证组件开发指令（给 Codex）

你现在是本项目 `frontend_h5` 与 `backend` 的协作开发工程师。请基于仓库现有代码，产出一套 **完整、美观、PC 与手机浏览器都稳定可用** 的滑块验证码组件与服务端配套能力。

## 一、总体目标

实现“短信验证码发送前必须先通过滑块验证”的完整链路，并满足以下要求：

1. 组件视觉与 `frontend_h5` 登录页风格一致（配色、字体、圆角、层次感统一）。
2. 交互稳定：支持鼠标拖动与触摸拖动，松手即校验。
3. 高并发下服务端无内存泄漏风险。
4. 失败重试友好：超过次数或超时才失效；失效后前端自动刷新。
5. 日志可控：滑块请求响应避免刷爆日志。

---

## 二、必须遵守的项目约束

1. 最小改动原则：不要无关重构。
2. 后端是 FastAPI + 异步架构：不得引入阻塞操作。
3. 业务异常按项目现有规范处理。
4. 组件实现优先复用现有 API 模块与工具方法。
5. 提交前必须补充并执行测试。

---

## 三、接口与数据契约（必须一致）

### 1）创建滑块挑战
- `POST /api/auth/slider-captcha/create`
- 请求体：
  - `phone: str`（11位）
  - `width: int`（前端容器可用宽度上报）
- 返回字段至少包含：
  - `captcha_id`
  - `width`
  - `height`
  - `block_size`
  - `block_y`
  - `background_image`
  - `slider_image`
  - `min_elapsed_ms`

### 2）校验滑块挑战
- `POST /api/auth/slider-captcha/verify`
- 请求体：
  - `phone`
  - `captcha_id`
  - `offset_x`
  - `elapsed_ms`
- 成功返回：
  - `captcha_ticket`
  - `expires_seconds`

### 3）发送短信验证码
- `POST /api/auth/send-code`
- 必须携带：
  - `phone`
  - `captcha_ticket`
- 逻辑：先验证 ticket，再执行短信发送。

## 四、服务端实现要求（重点）

### 1）缓存与防泄漏（必须）
使用内存缓存 challenge / ticket 时必须具备：

1. 过期清理：challenge、ticket 都要按 TTL 清理。
2. 上限保护：缓存条目数超过阈值时淘汰最旧记录。
3. 并发安全：使用异步锁保护读写。
4. 失败次数控制：
   - 同一 challenge 失败可重试。
   - 超过 `CAPTCHA_SLIDER_CHALLENGE_MAX_FAILS` 后失效。
   - 默认 `3`，支持 `.env` 配置。
5. 成功后失效：challenge 校验成功立即销毁，ticket 单次消费。

### 2）配置项（保留可配）
确保以下项可从配置读取：

- `CAPTCHA_SLIDER_TOLERANCE_PX`（默认 5）
- `CAPTCHA_SLIDER_MIN_ELAPSED_MS`（建议 800~1200）
- `CAPTCHA_SLIDER_CHALLENGE_EXPIRE_SECONDS`
- `CAPTCHA_SLIDER_CHALLENGE_MAX_FAILS`（默认 3）
- `CAPTCHA_SLIDER_TICKET_EXPIRE_SECONDS`
- `CAPTCHA_SLIDER_MIN_WIDTH`
- `CAPTCHA_SLIDER_MAX_WIDTH`
- `CAPTCHA_SLIDER_HEIGHT`
- `CAPTCHA_SLIDER_BLOCK_SIZE`

### 3）短信发送 mock 支持（必须）
`send-code` 链路继续支持 `SMS_CODE_MOCK_ENABLED`，不可破坏现有 mock 行为。

### 4）日志控制（必须）
滑块验证码高频接口响应体不要打详细日志（尤其不要记录 base64 图像），避免日志膨胀。

## 五、前端组件实现要求（重点）

### 1）布局与适配

1. 组件作为 `login-container` 的子层，不要全屏脱离容器。
2. PC 与移动端都要可用：
   - 不出现宽度溢出或过宽。
   - 不出现底部/左右异常空隙（除非设计明确保留）。
3. 宽度上报规则：按组件容器可用宽度 `100%` 上报，再由后端 clamp。

### 2）交互规范

1. 点击“发送验证码” -> 打开滑块层并请求 challenge。
2. 拖动方式：直接拖滑块本体（不要 range 轨道，不要蓝色轨道点）。
3. 松手即提交校验（无需“验证并发送”按钮）。
4. 校验失败：滑块自动回到起始位置。
5. challenge 失效（过期/超次）时：自动刷新 challenge。
6. 校验成功：自动发送短信并开始冷却倒计时。

### 3）视觉规范

1. 滑块层背景、标题、按钮颜色与登录页风格一致。
2. “刷新”按钮为 link 风格：
   - 无边框
   - 透明背景
   - 文本色与主题一致
3. 去掉“关闭”按钮（如果产品又要求可关闭，再通过外层点击遮罩关闭）。
4. 镂空区和滑块图要可辨识：
   - 镂空区底色略深于背景，便于识别
   - 滑块图保留边框（按当前体验结论）

---

## 六、已知坑位（必须规避）

1. 不要让 challenge 在“第一次失败”就立即销毁。
2. 不要把 popup 直接挂 body 并全宽，PC 下会难看。
3. 不要让镂空和滑块尺寸不一致（会导致无法对齐）。
4. 不要记录滑块 base64 响应日志。
5. 不要破坏短信 mock 发送开关。

---

## 七、验收标准

完成后必须满足：

1. 手机与 PC 浏览器都能顺畅拖动并成功验证。
2. 失败可重试，达到阈值后失效并自动刷新。
3. 滑块 UI 与登录页风格统一，无突兀控件。
4. 发送短信仍支持 mock 模式。
5. 日志量明显可控，不出现滑块响应刷日志。
